# Database design

PostgreSQL is the system of record and the job queue. Redis is intentionally absent. SQL migrations in `database/migrations/` are the schema source of truth. SQLAlchemy models map those tables. The application does not call `create_all`.

The runner is `python -m northstar.migrate`. It creates `schema_migrations` if needed, takes advisory lock `4993`, and applies each `*.sql` file in name order inside its own transaction. Dollar-quoted function bodies are not split on semicolons. A second run is a no-op.

## Tables

### jobs

| Column | Purpose |
| --- | --- |
| `id` | UUID primary key, generated by the API |
| `job_type` | `sort`, `shortest_path`, `word_frequency`, or `fibonacci` |
| `status` | `queued`, `running`, `succeeded`, `failed`, `retrying`, `cancelled` |
| `input_payload` | Validated, canonical JSON. Always present |
| `result_payload` | JSON result, SQL NULL unless the status is `succeeded` |
| `error_summary` | User-facing text, at most 400 characters. Required when `failed` |
| `retry_count`, `max_retries` | Attempts already consumed, and the budget copied at insert |
| `version` | Optimistic concurrency token, starts at 1 |
| `worker_id` | Owner while `running` |
| `idempotency_key`, `idempotency_fingerprint` | Both null or both set. The key is unique |
| `created_at`, `updated_at` | Required timestamps |
| `started_at` | Set on the first claim. Required once the job has been running |
| `finished_at` | Required for terminal states, null while open |
| `lease_expires_at` | Deadline for the current running attempt |

`result_payload` uses JSONB. The ORM sets `none_as_null` so a Python `None` is SQL NULL. A JSON `null` inside a successful result, such as an unreachable distance, stays JSON null. The check `jobs_result_matches_status` compares with SQL `IS NULL`, which does not treat JSON null as absent.

### job_attempts

One row per claim. `attempt_number` is `retry_count + 1` at claim time and is unique per job. Status is `running`, `succeeded`, or `failed`. History remains after a later retry. Deleting a job cascades to its attempts.

### job_events

Append-only audit of transitions: `from_status`, `to_status`, `reason`, `worker_id`, `created_at`. Reasons are short labels, at most 80 characters. Payloads are not copied here.

## Indexes

| Index | Use |
| --- | --- |
| `jobs_claim_idx` on `(created_at, id)` where status is queued or retrying | The claim query |
| `jobs_created_at_idx` | Recent-job listing |
| `jobs_status_updated_idx` on `(status, updated_at)` | Recovery and operator scans |
| `jobs_idempotency_key_idx` | Unique key. SQL NULL keys do not collide |
| `job_attempts_job_idx`, `job_events_job_idx` | History for one job |

## Invariants

Checks on `jobs` keep the row interpretable even if an application bug skips a field:

- Known job type and status.
- `0 <= retry_count <= max_retries <= 5` and `version >= 1`.
- A result exists exactly when the status is `succeeded`.
- `failed` has an error summary.
- Terminal rows have `finished_at`. Open rows do not.
- `queued` and `cancelled` may lack `started_at`. Every other status has it.
- `running` has a worker id.
- The idempotency key and fingerprint are a pair.

The trigger `enforce_job_status_transition` allows only:

- `queued` to `running` or `cancelled`
- `retrying` to `running` or `cancelled`
- `running` to `succeeded`, `retrying`, or `failed`

Updating a column other than `status` does not fire the trigger. An illegal status change raises `check_violation` with detail `old -> new`. The detail is built with `||` rather than a `%` placeholder so psycopg does not treat it as a format string.

## Time

Columns are `timestamptz`. Connections run `SET TIME ZONE 'UTC'`. The application writes `datetime.now(UTC)`.

## Why a database queue

The lab needs a durable queue, a history table, and a transaction that can lock a job and insert an attempt together. PostgreSQL already provides that. A second broker would add a failure mode the course does not need and would split the source of truth.
